## Бэкенд `backend/app.py`

### 1. SQL-инъекции

- **Риск:** Нет.
- **Рекомендация:** не требуется.
- **Статус:** OK.

### 2. Хеширование паролей
- **Найдено:** PBKDF2-HMAC-SHA256, соль случайная на каждого пользователя, 100 000 итераций (`_hash_password`/`_new_salt`). Корректно.
- **Риск:** Нет.
- **Рекомендация:** не требуется.
- **Статус:** OK (надёжно).

### 3. Срок действия сессий
- **Найдено:** `fc_sessions` не имела поля/проверки срока действия — токен из `secrets.token_hex(32)` был валиден бессрочно.
- **Риск:** Средний.
- **Рекомендация:** ввести cutoff по сроку сессии (например 30 дней), проверять при авторизации и удалять протухшие сессии.
- **Статус:** **ИСПРАВЛЕНО.** Добавлен `SESSION_TTL_SECONDS = 30 дней`; `_session_expired()` по ISO `created` (неразбираемые метки считаются истёкшими); `_acting_user()` возвращает `None` и удаляет протухшую сессию; при старте `init_db()` разово вычищает протухшие сессии. Проверено: валидный токен по-прежнему даёт `200` на `/api/me`.

### 4. Ограничение частоты логина/регистрации
- **Найдено:** нет ограничений — возможен перебор паролей и перечисление имён (409 «taken» против 200).
- **Риск:** Средний.
- **Рекомендация:** in-memory (в процессе) троттлинг по IP клиента для `/api/auth/login` и `/api/auth/register`, без внешних зависимостей.
- **Статус:** **ИСПРАВЛЕНО.** Добавлен `_rate_limited(ip)`: словарь + `threading.Lock`, `time.monotonic()`, лимит 10 попыток за 60-секундное окно на IP; при превышении — `429`. Применён к `login` и `register`. Проверено: после ~10+ неудачных логинов сервер отдаёт `429`.

### 5. Защита статики от path-обхода (`_serve_static`)
- **Найдено:** префиксная проверка `startswith(normpath(DIST_DIR))` без завершающего разделителя — sibling-каталог вида `distX/...` мог пройти проверку и дать чтение за пределами `dist`.
- **Риск:** Низкий—Средний.
- **Рекомендация:** отвергать сегмент `..` и проверять префикс с `os.sep`.
- **Статус:** **ИСПРАВЛЕНО.** 1) сегмент `..` в `clean.split(os.sep)` ведёт к `index.html`; 2) префиксная проверка заменена на `file_path != dist_root and not file_path.startswith(dist_root + os.sep)`. Проверено: файл-«проба» в sibling-каталоге `distX` НЕ отдаётся, обычный `GET /` по-прежнему отдаёт `index.html` (200).

### 6. Привилегия администратора по саморегистрации (HIGH — реальная дыра)
- **Найдено:** `POST /api/auth/register` присваивал `role='admin'`, если `username == 'Danya'` — любой мог зарегистрироваться как «Danya» и получить права администратора (удалять/редактировать ЛЮБОЙ набор через гейт K21). Дополнительно `init_db()` продвигал любую строку «Danya» в админа.
- **Риск:** Высокий.
- **Рекомендация:** регистрация никогда не должна выдавать админа по самоизбранному имени; роль `'user'` всегда. Админ — только предсозданный/внешний аккаунт.
- **Статус:** **ИСПРАВЛЕНО.** (a) регистрация всегда создаёт роль `'user'`; (b) `init_db()` продвигает в админа только уже существующую строку `Danya` (не создаёт её); (c) **дополнительно** исправлен `_is_admin()` — убран жёстко прописанный `if username == "Danya": return True`; решение принимается только по роли из БД. Без (c) саморегистрация под ником Danya всё ещё давала бы админа — это было необходимо для фактического закрытия дыры.
  - Проверено: зарегистрированный «Danya» получает `403` при удалении чужого набора (нет админ-прав); обычный пользователь получает `403`; предсозданный аккаунт «Danya» (роль была `'user'`, продвинут `init_db()`) логинится и успешно удаляет чужой набор (`200`) — намерение K21 сохранено.

### 7. Гейт авторизации при DELETE / добавлении карточек (K21)
- **Найдено:** DELETE и `POST /api/sets/{id}/cards` гейтятся на сервере через `_is_admin` + совпадение автора. Серверная проверка есть.
- **Риск:** Нет (после исправления #6).
- **Рекомендация:** после закрытия дыры #6 гейт работоспособен.
- **Статус:** OK (после #6).

### 8. Наборы с `author NULL` (до K18)
- **Найдено:** без роли админа удаляет только автор; для наборов с `author NULL` не-админ удалить не может, админ — может. Минорно.
- **Риск:** Низкий.
- **Статус:** Только документирование (по ТЗ).

### 9. Заголовки безопасности
- **Найдено:** не отдавались вовсе.
- **Риск:** Низкий.
- **Рекомендация:** добавить базовые заголовки безопасности и CSP.
- **Статус:** **ИСПРАВЛЕНО.** В `_send_bytes()` добавлены: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'`. `Cache-Control: no-store` сохранён. Проверено: заголовки отдаются; `npm run build` проходит (ветка React имеет инлайн-стили — `style-src 'unsafe-inline'` включён обоснованно); `index.html` отдаётся с этими заголовками.
